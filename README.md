#  MuhideenShield SOC Lab

MuhideenShield SOC Lab is a hands-on Security Operations Center (SOC) project I built to develop practical experience in security monitoring, log analysis, detection engineering, troubleshooting, and incident investigation.

The lab uses **Kali Linux as a monitored endpoint** and **Splunk Enterprise as the SIEM platform**. Linux security logs are collected using the **Splunk Universal Forwarder** and sent to Splunk for analysis.

The project documents the complete process, including configuration, log forwarding, troubleshooting, security investigations, detection development, and lessons learned.

---

##  Project Objectives

The main objectives of this project are to:

* Build a functional SOC monitoring environment.
* Collect security logs from a Linux endpoint.
* Forward Linux logs to a SIEM platform.
* Analyze authentication and system activity.
* Investigate successful and failed SSH login attempts.
* Develop basic security detections.
* Practice incident investigation and documentation.
* Improve my understanding of SIEM operations and SOC workflows.
* Document technical problems and how they were resolved.

```text
Kali Linux

The Splunk Universal Forwarder collects logs from Kali Linux and forwards them to Splunk Enterprise running on the macOS host.

```

The authentication log provides information about activities such as:

* SSH login attempts
* Successful authentication
* Failed authentication

* CRON activity
* Authentication-related system events

Example command used to inspect the logs directly:

```bash
sudo tail -20 /var/log/auth.log
```

This allows me to compare events appearing locally on Kali Linux with events received by Splunk.

## 🔄 Splunk Universal Forwarder Configuration

The Splunk Universal Forwarder was configured on Kali Linux to send logs to the Splunk Enterprise instance running on the host machine.

The forwarding connection used:

```text
Splunk Receiver: 172.20.10.2
Port: 9997
```

The forwarding status was verified using Splunk Universal Forwarder commands.

A successful configuration showed:

```text
Active forwards:
172.20.10.2:9997
```

Network connectivity to the Splunk receiver was also tested using Netcat:

```bash
nc -vz 172.20.10.2 9997
```

The successful test confirmed that TCP port `9997` was reachable between the Kali Linux VM and the Splunk server.

> **Note:** The IP addresses shown belong to the isolated lab environment and may change depending on the network configuration.

## 🔍 Security Monitoring and Investigation

After successfully forwarding the logs, I used Splunk to investigate security events generated by the Kali Linux system.

The investigation included analyzing:

* Successful SSH authentication
* Failed authentication attempts
* Login sources
* User activity
* Authentication timestamps
* Commands and system activity
* Suspicious events
* Patterns across multiple log entries

One example identified during the lab was a successful SSH authentication event.

```text
Accepted password for kali from <LAB-IP> port <PORT> ssh2
```

From events like this, I can identify:

* The account involved
* Authentication method
* Source IP
* Source port
* Timestamp
* Whether authentication succeeded or failed

This simulates part of the investigation process a SOC analyst may perform when reviewing authentication activity.

## 🛠️ Troubleshooting and Challenges

Building the lab involved several technical challenges.

### Splunk Forwarder Connectivity

I needed to confirm that Kali Linux could communicate with the Splunk receiver.

I tested TCP port `9997` using:

```bash
nc -vz 172.20.10.2 9997
```

The successful connection confirmed that the network path between the endpoint and Splunk was working.

### Confirming the Forwarder

I verified that the Splunk Universal Forwarder was configured correctly and that the Splunk server appeared under active forwards.

### Log Verification

Linux authentication logs were inspected directly using commands such as:

```bash
sudo tail -20 /var/log/auth.log
```

This helped verify that security events existed locally before investigating whether they were being received by Splunk.

### Splunk Licence Limitation

During the project, the Splunk Enterprise licence used for the lab expired.

Instead of abandoning the project, I preserved screenshots and documentation from the previous Splunk analysis and continued documenting the Linux logs, forwarding configuration, connectivity tests, and investigation process.

This became an additional lesson in troubleshooting and maintaining evidence during a lab environment failure or limitation.

## 📚 Lessons Learned

Building MuhideenShield has reinforced several important lessons.

Security monitoring is not simply about installing a SIEM. Logs must first be generated, collected, transported correctly, searched, interpreted, and correlated before they become useful security information.

I also learned the importance of validating each stage of a monitoring pipeline individually.

For example:

```text
Are logs being generated?
        ↓
Is the forwarder running?
        ↓
Can the endpoint reach the SIEM?
        ↓
Is the receiving port open?
        ↓
Is Splunk receiving the data?
        ↓
Can the events be searched?
        ↓
What does the activity mean?
```

This troubleshooting approach helped me understand the relationship between endpoints, networks, log collectors, and SIEM platforms.
